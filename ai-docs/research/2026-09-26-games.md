# Building games with three.js in 2026

Date: 2026-09-26
Track: games. Stack, loop, performance, assets, multiplayer, the vibe coding wave, distribution and automated testing, for the threewright `game-starter` template and the `threewright-games` skill.
Status: first pass. Versions and publish dates come from the npm registry (`npm view <pkg> version time --json`, queried 2026-09-26) unless noted. Claims marked "unverified" were not confirmed against a primary source. Several official pages (Poki, CrazyGames, itch.io, levels.io, vibejam.com, colyseus.io, rapier.rs, threejs.org, MDN) could not be fetched directly from this session; where their content was read only through search result summaries, the text says so. GitHub and raw GitHub sources were read directly. Measurements marked "measured" were run in this container on 2026-09-26 (Node 22.22.2, Chromium 141.0.7390.37 with SwiftShader, Vite 8.3.1, Playwright core 1.63.0).

## Summary

- Plain three.js 0.186.1 plus Rapier is the right default for an agent. It has the fewest moving parts and the most examples, and tw can inspect it with no page changes. React Three Fiber 9.8.1 is right when the project is already React. Babylon.js 9 and PlayCanvas 2 are engines, not renderers; they fit teams that want an editor or batteries included. Meta IWSDK 1.0 is the pick for Quest-first XR games.
- Rapier JS 0.21.0 shipped on 2026-09-25 (changelog dated 24 September 2026). It adds soft bodies and moves the bindings into the main `dimforge/rapier` repo. The `-compat` bundle grew from 614 KB (0.19.3) to 1.19 MB brotli (measured), and snapshots from older versions no longer load. It passed a character controller, snapshot and restore test here in Node 22 and in Chromium 141.
- `THREE.Clock` is deprecated since r183 (three 0.183.0, 2026-02-18). Use `THREE.Timer` with `timer.connect(document)`. `PCFSoftShadowMap` was removed in r186 and now warns and falls back to `PCFShadowMap`. r186 adds `SunLight`, a sun with two cascaded shadow maps, as an addon.
- The official physics demos are demos, not game loops. `RapierPhysics.js` loads Rapier 0.17.3 from Skypack and steps it with `setInterval` and a variable dt. The Rapier character controller example moves by `1/60` per rendered frame, so it runs twice as fast on a 120 Hz screen. Agents copy these files; the skill must say not to.
- A fixed timestep with an accumulator and render interpolation is the standard. IWSDK's Havok system does exactly this (60 Hz default, at most 4 steps per frame, interpolation alpha), which makes it a good current reference.
- AI-made games fail in predictable ways: they do not load, they sit behind a loading screen, they break inside an iframe, they have no touch controls, movement depends on frame rate, collisions use distance checks, and multiplayer trusts the client. In the 2025 Vibe Jam, pre-vetting cut 1,000+ entries to about 500 "based on rules (many games didn't even load)".
- Web portals set hard limits. Poki asks for an initial download under 8 MB. CrazyGames allows 50 MB initial (20 MB for its mobile homepage) and disables games that do not run smoothly on 4 GB Chromebooks. (Both come from their docs as quoted in search results.) Discord Activities allow WebSockets only; their docs say WebRTC is not supported.
- Automated game testing works when the game exposes hooks. Measured here: with Playwright's `page.clock.install()` and `pauseAt()` called before navigation, three reloads of a Rapier game with the same seed and the same key presses produced the same physics snapshot hash. With the clock installed but not paused before load, real time leaked in and runs differed. Pausing the game and calling a `step(n)` hook also gave identical hashes.

Rapier facts verified here (Node 22 and Chromium 141, version 0.21.0):
- Init: `import RAPIER from '@dimforge/rapier3d-compat'; await RAPIER.init();` took about 115 ms in Node.
- The non-compat `@dimforge/rapier3d` imports its `.wasm` as an ES module. Vite 8.3.1 bundled it with no plugin and it ran in Chromium 141. Node needs the compat build (or wasm module support).
- Character controller API: `world.createCharacterController(offset)`, `enableAutostep(maxHeight, minWidth, includeDynamicBodies)`, `enableSnapToGround(distance)`, `setMaxSlopeClimbAngle(radians)`, `computeColliderMovement(collider, desiredDelta)`, `computedMovement()`, `computedGrounded()`. Drive a kinematic position-based body with `setNextKinematicTranslation`.
- A world with 200 balls, a ground and a character serialized to a 268 KB `Uint8Array`. Restore and re-snapshot gave identical bytes. Two runs in one process gave the same hash. The default build and the deterministic build gave different hashes for the same scene, so different builds are different determinism domains.
- 600 steps of that world took about 0.5 to 0.6 s in Node here (about 1 ms per step). No claim for phones.
- `world.timestep` defaults to 1/60. Keep it fixed.

Official three.js physics code to avoid copying into a game:
- `examples/jsm/physics/RapierPhysics.js` (dev branch): `RAPIER_PATH = 'https://cdn.skypack.dev/@dimforge/rapier3d-compat@0.17.3'`, then `setInterval( step, 1000 / frameRate )` with `world.timestep = timer.getDelta()`. Old version, third-party CDN, variable dt, and timers that browsers throttle in background tabs.
- `examples/physics_rapier_character_controller.html`: `const deltaTime = 1 / 60;` inside the render loop, no gravity on the character, and it calls `setTranslation` on the collider directly.

## 2. Core loop patterns

### 2.1 Fixed timestep, interpolation, Timer

The pattern (Fiedler, "Fix Your Timestep!"): accumulate real time, run the simulation in fixed steps, render with interpolation between the last two simulation states. Clamp the frame delta and cap steps per frame so a slow frame cannot spiral.

```js
const STEP = 1 / 60, MAX_STEPS = 4;
const timer = new THREE.Timer();
timer.connect(document); // Page Visibility: no giant delta after a hidden tab
let acc = 0;
renderer.setAnimationLoop((time) => {
  timer.update(time);
  const dt = Math.min(timer.getDelta(), 0.25);
  if (!paused) {
    acc += dt * timeScale;
    let n = 0;
    while (acc >= STEP && n < MAX_STEPS) { input.sample(); sim.step(STEP); acc -= STEP; n++; }
    if (n === MAX_STEPS) acc = 0; // drop time instead of spiraling
  }
  view.sync(acc / STEP); // lerp previous to current transforms
  renderer.render(scene, camera);
});
```

- `THREE.Timer` is in core (`src/core/Timer.js`, exported from `three`). Call `update(timestamp)` once per frame, then `getDelta()` and `getElapsed()` in seconds. `setTimescale()` scales deltas. `connect(document)` resets the timer when the page becomes visible again. `dispose()` disconnects.
- `THREE.Clock` logs "Clock: This module has been deprecated. Please use THREE.Timer instead." since r183 (PR #32798, and #32793 replaced Clock with Timer across addons and examples). threewright's lint rules already carry a `clock` rule.
- IWSDK's `PhysicsSystem` (main branch) uses the same shape: `DEFAULT_UPDATE_FREQUENCY = 60`, `MAX_UPDATE_FREQUENCY = 240`, `MAX_ACCUMULATED_STEPS = 4`, and an interpolation alpha of `stepAccumulator / stepInterval`.
- `renderer.setAnimationLoop` is required for WebXR. WebGPURenderer's version is async. Stop with `setAnimationLoop(null)`.
- Put mouse look in the render frame (low latency) and movement in the fixed tick (stable). Read the latest yaw inside the tick.
- Never scale movement by a per-frame constant such as `1/60`. Never compute physics from `Date.now()`.

### 2.2 Pausing and hidden tabs

- Browsers stop `requestAnimationFrame` in hidden tabs, so the loop stops by itself. Background timers are throttled, which is another reason not to step physics from `setInterval`.
- On `visibilitychange` to hidden: pause gameplay, suspend the `AudioContext`, and tell the portal SDK (`gameplayStop`). On return, show the pause menu instead of resuming an action game mid-fight.
- Treat pointer lock loss as a pause request, because Esc always unlocks.

### 2.3 Input

Build an action map. Actions (`moveX`, `moveY`, `lookX`, `lookY`, `jump`, `fire`, `interact`, `pause`) read from bindings on each device. Save rebinding in settings. Track the last used device to switch on-screen prompts.

- Keyboard: use `KeyboardEvent.code`. It names the physical key, so the WASD block still works on AZERTY, where those keys are labelled ZQSD. Keep a `Set` of held codes. Clear it on `blur` so keys do not stick.
- Pointer lock (MDN browser-compat-data, 2026-09-26): Chrome 37+ (returns a Promise since 92), Firefox 50+, Safari 10.1+ (Promise since 18.4), no support in iOS Safari. `unadjustedMovement` (raw mouse): Chrome 88 (not on Linux), Firefox 152, Safari 18.4. It needs transient activation (a click). The browser always unlocks on Esc. MDN: calling `requestPointerLock()` right after the default unlock gesture "will fail, even if a transient activation is available". Call `requestPointerLock()` before `requestFullscreen()`, because fullscreen consumes the activation.
- Gamepad: poll `navigator.getGamepads()` every frame; there are no change events for buttons. Use the `standard` mapping and a radial dead zone (about 0.15 is a common convention, unverified as a standard). Rumble through `vibrationActuator` works in Chrome 68+ and Safari 16.4+ on desktop, not in Firefox, not on iOS (BCD).
- Touch: detect with `matchMedia('(pointer: coarse)')`, use pointer events, set `touch-action: none` on the canvas, and keep controls inside safe areas. nipplejs 1.0.4 (2026-05-26) is a TypeScript rewrite (1.0.0 on 2026-03-21) with multitouch dual sticks; handlers changed to `(evt) => evt.data`, and `maxNumberOfNipples` became `maxNumberOfJoysticks`. Poki asks that mobile controls be forced on tablets (search summary).
- Screen orientation lock works on Chrome for Android and Firefox 144+, not in Safari (BCD). Design for both orientations or show a rotate hint.

### 2.4 Camera rigs

- Third person, spring arm: keep a pivot above the player. Cast from the pivot toward the desired camera spot with Rapier (`castRay` or `castShape`, excluding the player's collision group). Place the camera at the hit distance minus a margin. Smooth with a frame-rate independent factor `1 - Math.exp(-k * dt)`. Pull in fast, ease out slow.
- First person: yaw on the body, pitch on the camera, clamp pitch to about plus or minus 89 degrees, apply sensitivity and invert Y from settings. `PointerLockControls` is fine; a custom handler with `movementX` and `movementY` is equally short.
- Orbit and editor cameras: `camera-controls` 3.1.2 (2025-11-17) or `OrbitControls`. Not for gameplay cameras.

### 2.5 Audio

- Use three's Web Audio wrappers: one `AudioListener` on the camera, `PositionalAudio` on emitters, and the shared context from `THREE.AudioContext.getContext()`.
- Autoplay unlock: create or `resume()` the context inside the first `pointerdown`, `keydown` or `touchend`. Mute until then.
- iOS: the silent switch mutes Web Audio in the default "ambient" session. Setting `navigator.audioSession.type = 'playback'` before the context starts avoids that. Only Safari 16.4+ implements `navigator.audioSession` (BCD). The workaround is widely used in open source pull requests and in feross/unmute-ios-audio (unverified in WebKit documentation).
- Suspend the context on hidden tabs and pause menus.
- Howler 2.2.4 (2023-09-19) is unmaintained: the maintainer's last update post in the project's "Update on updates" discussion is from 2022-04-29, with unanswered follow-ups through June 2026. It still works for simple sound effects, but three's audio is enough.

### 2.6 Save state, settings, pause menu, fullscreen, UI

- Save: JSON in `localStorage` with a schema version and migrations, wrapped in try/catch (storage can throw in private windows and partitioned iframes). IndexedDB for larger data. CrazyGames offers a cloud `data` module (search summary). Never store raw physics snapshots in player saves; Rapier 0.21 cannot read older snapshots.
- Settings: master, music and effects volume; mouse sensitivity; invert Y; quality preset (pixel ratio cap, shadows, shadow map size); reduced motion (no camera shake); key bindings; touch control size and side.
- Pause menu: opens on Esc, pointer lock loss, gamepad Start and hidden tab. Stops ticks. Resume needs a click to re-lock the pointer.
- Fullscreen: `requestFullscreen()` needs a gesture. On iPhone there is no element fullscreen: BCD says "Only available on iPad, not on iPhone" and notes an overlay button and swipe-to-exit that make it "unsuitable for some use cases like games". On iOS, the full-screen path is an installed PWA. CrazyGames provides fullscreen itself (search summary).
- UI overlays: HTML and CSS over the canvas. Container `pointer-events: none`, controls `pointer-events: auto`. Update HUD text only when a value changes. Respect `env(safe-area-inset-*)`, and in Discord the `--discord-safe-area-inset-*` variables.

## 3. Performance for games

### 3.1 Budgets

| Target | Draw calls | Geometry | Source |
| --- | --- | --- | --- |
| Mid phone | under 100 | under 100k vertices | Don McCurdy's rule, quoted by Utsubo (2026-09-11) |
| Desktop | a few hundred to low thousands; one summary says under 500 | 500k to 1M triangles on screen | Utsubo (search summary) |
| Quest (native guideline) | 500 to 1,000 maximum | 1 to 2M triangles or vertices maximum | Meta performance guidelines (search summary); WebXR needs to stay well under this |

threewright presets (suggestions, not industry numbers): `low` for phones and Chromebooks (pixel ratio 1 to 1.5, 100 draw calls, 150k triangles, shadows off or one 1024 map) and `high` for desktop (pixel ratio up to 2, 500 draw calls, 1M triangles, SunLight with 2048 cascades).

Bundle weight (measured, Vite 8.3.1 production build): a bare `WebGLRenderer` app was 523 KB minified, 106 KB brotli. three.js WebGL plus GLTFLoader, KTX2Loader and the Meshopt decoder came to 698 KB minified, 184 KB gzip, 151 KB brotli. Adding Rapier 0.21.0 compat added 4.33 MB minified, 1.64 MB gzip, 1.19 MB brotli. The basis transcoder is 204 KB brotli and the Draco decoder 49 KB brotli, loaded only when a texture or mesh needs them. The three 0.186.1 npm package ships no minified `build/*.min.js` files; a bundler minifies.

### 3.2 Techniques

- InstancedMesh: one geometry and one material, one draw call. `@three.ez/instanced-mesh` 0.3.16 (2026-07-26) adds per-instance frustum culling, sorting, BVH raycasting and LOD.
- BatchedMesh: many geometries with one material, per-instance visibility and color. r183 added per-instance opacity and wireframe support; r186 fixed draw offsets and visibility updates. The `SceneOptimizer` addon (`three/addons/utils/SceneOptimizer.js`) is "an experimental attempt to implement auto-batching". The `webgl_batch_lod_bvh` example pairs BatchedMesh with `@three.ez/batched-mesh-extensions` 0.0.12 (2026-06-23).
- LOD: `THREE.LOD`, the `webgl_lod` and `webgl_loader_gltf_progressive_lod` examples, and `gltf-transform optimize --simplify`.
- Frustum culling is on by default. Skinned meshes cull by bounding sphere; recompute it after loading or characters can pop at screen edges (common forum issue, unverified for r186 specifics).
- Occlusion: WebGPURenderer supports occlusion queries (`webgpu_occlusion`); r186 "Make occlusion queries more robust" (#33972). With WebGLRenderer, design levels as rooms and cull by distance or room.
- Textures: KTX2 (ETC1S for color, UASTC for normals). In r186 `KTX2Loader` and `DRACOLoader` resolve their decoders with `new URL(..., import.meta.url)` by default, so a bundler copies them. Do not call `setTranscoderPath('/basis/')` unless those files are really there.
- Shader warm-up: `await renderer.compileAsync(scene, camera)` behind the title screen. r185 fixed `compileAsync()`; r186 lets WebGLRenderer's `compile()` handle node materials and adds `compileComputeAsync()`. Spawn each effect once off screen to warm its program.
- Garbage: preallocate scratch vectors and quaternions, no `new` in update code, pool projectiles and particles (reuse slots of an InstancedMesh with `count`), no per-frame closures or `Array.map` in hot paths.
- WebGPU compute particles: TSL compute examples (`webgpu_compute_particles`, `_rain`, `_snow`, `_fluid`). WebGPURenderer's WebGL2 fallback runs compute through transform feedback with limits (the count must be a single number; no indirect storage buffers), per `WebGLBackend.compute()` in r186.
- Shadows: every shadow-casting light adds depth passes (six for a point light). Use one sun. `SunLight` (r186 addon, `three/addons/lights/SunLight.js`) has no target, shines from its position toward the origin, uses 2 cascades at 1024 per cascade by default, and fits cascades to the view frustum up to `camera.far`. With WebGPURenderer it needs `renderer.library.addLight( SunLightNode, SunLight )`. The older CSM addon (`examples/jsm/csm`) and `CSMShadowNode` remain. For static levels set `renderer.shadowMap.autoUpdate = false` and flag updates, or bake lightmaps. `PCFSoftShadowMap` is removed in r186.
- Measure: `renderer.info` (calls, triangles, memory). stats-gl 4.2.3 (2026-07-10) shows FPS, CPU and GPU timing for WebGL and WebGPU (its README still shows `renderAsync`, deprecated since r181). r3f-perf 7.2.3 (2024-11-08) depends on drei ^9 and zustand ~4.5 and looks stale for R3F 9 (unverified breakage); drei's `StatsGl` is the safer R3F choice.
- Pixel ratio: cap at 2, drop to 1.5 or 1 when frame time stays over budget (dynamic resolution).
- r186 adds `Object3D.dispose()` (#34141) for the object's own GPU resources; geometries, materials and textures still need their own `dispose()` on level unload.

### 4.2 glTF pipeline

- `gltf-transform optimize in.glb out.glb --compress meshopt --texture-compress ktx2 --texture-size 1024` (@gltf-transform/cli 4.5.0, 2026-09-01). KTX2 needs the `ktx` command from KTX-Software; without it use `--texture-compress webp`.
- Other `optimize` flags that matter for games: `--join` (needs `--flatten`) to cut draw calls, `--instance` for repeated meshes, `--simplify` with `--simplify-ratio`, `--palette` to merge flat materials, `--prune`.
- `gltf-transform inspect` for a text summary; never paste binaries into context.

### 4.3 Characters and animation

- Clone skinned characters with `SkeletonUtils.clone(gltf.scene)` (`three/addons/utils/SkeletonUtils.js`); a plain `clone()` breaks the skeleton binding.
- One `AnimationMixer` per character, updated with the frame delta.
- Crossfade: `next.reset().play(); current.crossFadeTo(next, 0.2, true);` (`crossFadeTo(fadeInAction, duration, warp)` in r186). Drive the state machine from gameplay state (idle, run, jump, fall, land), not from input.
- Keep gameplay movement in the controller. Strip root motion from locomotion clips or ignore root translation (common practice, unverified as a three.js recommendation).

### 4.4 Level building

- Blender custom properties export as glTF `extras`, and GLTFLoader copies them to `object.userData` (`assignExtrasToUserData` in r186). Use naming and props such as `col_*` (collision only), `spawn_*`, `trigger_*`, `userData.collider = 'trimesh'`.
- Build Rapier colliders from simplified collision meshes: `trimesh` for static level geometry, primitives or `convexHull` for dynamic props. Never collide against the full render mesh.
- The three.js editor exports GLB for quick layouts. Needle Engine for Blender 1.0.0 (July 2026, search summary) and Needle for Unity add component authoring.

### 4.5 Procedural generation

- Seeded PRNG (mulberry32 or sfc32). Never `Math.random()` in generation or simulation.
- Noise: three's `SimplexNoise.js` and `ImprovedNoise.js` addons (`three/addons/math/`), or simplex-noise 4.0.3 (2024-07-26), which takes a random function for seeding.
- Generation must be a pure function of the seed so tests can replay it. Render tiles with InstancedMesh or BatchedMesh.
- Navigation: recast-navigation 0.43.1 (2026-02-04) and @recast-navigation/three 0.43.1 (2026-04-07); navcat 0.4.1 (2026-05-06), pure JS from the same author per its npm repository field; yuka 0.7.8 (2022) and three-pathfinding 1.3.0 (2024-05-17) are old.

## 5. Multiplayer

### 5.1 Models

- Relay: each client broadcasts its own state. Fine for co-op toys. Trivially cheatable.
- Authoritative server: the server simulates, clients send inputs. Required for anything competitive or monetized.
- Lockstep or rollback: every peer runs a deterministic simulation from inputs only. Needs a deterministic physics build and strict input timing.

### 5.2 Libraries and transports

### 5.3 Authoritative Rapier in Node, prediction and interpolation

- `@dimforge/rapier3d-compat` runs in Node 22 (verified here). Share one `sim/` module between server and client.
- Tick at 30 or 60 Hz. Send snapshots at 10 to 20 Hz. Render remote entities about 100 ms in the past with snapshot interpolation (Valve's Source networking default of 100 ms; classic reference). `@geckos.io/snapshot-interpolation` 1.1.1 (2025-02-22) implements the buffer.
- Predict the local player, keep unacknowledged inputs, and replay them on each server correction (Gambetta, "Fast-Paced Multiplayer").
- Validate inputs on the server (speed limits, cooldowns), rate limit messages, never accept client positions, and put the server behind a DDoS-protecting proxy.

### 6.5 What went wrong, and lessons for an agent

Observed failure patterns:
- Games that did not load or needed heavy downloads (2025 pre-vetting).
- Games that broke inside an iframe (2026 judging workflow).
- Collision by distance checks instead of physics events, and camera code that did not adapt to new room sizes (a jam developer's write-up, search summary).

Lessons:
1. First interactive frame within seconds. Show the live world at once, stream the rest, no blocking loading screen.
2. Work inside an iframe with no login and no popups. Pointer lock and fullscreen only after a click.
3. Touch controls from day one.
4. Fixed timestep. No per-frame constants.
5. Physics events and queries, not distance checks.
6. Server authority for anything competitive or paid.
7. Build debug views and small editors early; the winner called that the biggest multiplier.
8. Support `?portal=true` spawning when targeting the jam.
9. Keep a smoke test that loads the game, presses keys and checks that the player moved.

## 8. Testing a game automatically

### 8.1 What others do

- three.js e2e (see the sister note on testing): Puppeteer, a deterministic `Math.random` injection, 400x250 screenshots, and a 0.1 percent pixel budget.
- OpenAI's `develop-web-game` skill (openai/skills, per skill directory listings; its current location in the repo is unverified): the game must expose `window.render_game_to_text()` returning a short JSON of what is on screen, and `window.advanceTime(ms)` for deterministic stepping; a Playwright client sends input bursts, captures screenshots and collects console errors. Loop: implement, act, pause, observe, adjust.
- IWSDK agent mode: `npx @iwsdk/cli dev up --ai-mode agent` runs a headless Playwright browser with a fixed viewport (default 800x800). The main-branch docs list about 47 MCP tool names, including `browser_screenshot`, `browser_interact`, `browser_get_console_logs`, `xr_set_gamepad_state`, and `ecs_pause`, `ecs_step`, `ecs_snapshot`, `ecs_diff` (count by grep, 2026-09-26). Suggested workflow: find the entity, pause, snapshot "before", step or act, snapshot "after", diff.
- playtest-lab (mhwangbo, GitHub, 3 commits, unverified maturity): an adapter with `create(seed)`, `observe`, `step`, `done`, `metrics`, `idleAction`, `randomAction` and `policies`; bots play many seeds on a fake clock and report p10, p50 and p90 metrics.

### 8.2 Measured here

Setup: a small three.js game (WebGLRenderer, Rapier 0.21.0 non-compat, kinematic character controller, 20 dynamic balls placed by a seeded PRNG, the fixed-step loop from section 2.1), built with Vite 8.3.1, served locally, driven by Playwright core 1.63.0 on Chromium 141 with `--use-angle=swiftshader --enable-unsafe-swiftshader`. The page exposed `window.__game` with `state()`, `step(n)`, `pause()` and `snapshotHash()` (SHA-256 of `world.takeSnapshot()`).

| Method | Result |
| --- | --- |
| `page.clock.install()`, load, then key presses with `clock.runFor()` | Player moved about 3.6 m for 1 s of held `KeyD`, but tick counts (103 vs 102) and hashes differed between reloads. Real time flowed until the test paused the clock. |
| `install()`, load, then `pauseAt()` after load | Ticks before the pause differed (5 vs 11), so hashes differed. |
| `install()` and `pauseAt()` before `page.goto()`, then `runFor(500)`, hold `KeyD` for `runFor(1000)`, `runFor(100)` | Three reloads, identical: tick 95, x 3.507, same hash. |
| Load, `__game.pause(true)`, `step(30)`, key down, `step(60)`, key up, `step(6)` | Two reloads, identical: tick 96, x 3.689, same hash. |

Playwright's clock overrides `Date`, timers, `requestAnimationFrame`, `requestIdleCallback`, `performance` and `Event.timeStamp` (Playwright docs source). Because three's animation loop calls `requestAnimationFrame` through `self`, the fake clock drives `renderer.setAnimationLoop`. The catch is order: freeze time before any page script runs. tw's virtual clock (used by `tw video`) replaces `performance.now`, `Date.now` and `requestAnimationFrame` at injection time and exposes `window.__tw.advance(ms)`, so it has the same property.

### 8.3 Recommended harness

- Deterministic seed from the URL (`?seed=`). No `Math.random()`, `Date.now()` or iteration order that depends on async load order in simulation code. Create physics bodies in a fixed order.
- A test mode (`?test=1`) that loads everything, starts in play mode on tick 0, paused, muted, at pixel ratio 1 and a fixed canvas size, with no title screen and no pointer lock requirement.
- Step hooks (`step(n)`) plus action-level input injection, so tests do not depend on rAF timing. Keep a real-key smoke test too, with the clock frozen before navigation.
- Scripted input playback: record per-tick action frames and replay them; assert on state and on the snapshot hash.
- Physics across machines: only `@dimforge/rapier3d-deterministic-compat` promises identical results on different machines (package README). With other builds, compare two runs on the same machine, or compare positions with a tolerance, instead of committing golden hashes. Values fed to physics from `Math.sin` and friends can differ across JS engines (ECMA-262 lets Math functions be implementation-approximated).
- Screenshots: canvas only, small (480x270), after a pause and a fixed number of steps, compared with a pixel ratio threshold (see the sister note). Use them for "is anything visible", not for gameplay logic.
- Smoke assertions that catch most broken agent games: no console errors; `__tw.ready` resolves; the player moves in the pressed direction; jump raises then lowers y; the player is grounded at rest; restart works; draw calls and memory stay flat across a restart.

### Skill rules (threewright-games)

1. Start from `templates/game-starter`. Keep the pins. Do not add a CDN import for physics.
2. Simulation runs in fixed ticks. Never scale movement by a per-frame constant. Use `THREE.Timer` with `connect(document)`. Never `THREE.Clock`.
3. All input goes through the action map. Use `event.code`. Poll gamepads. Show touch controls on coarse pointers. Pointer lock only on click; unlock means pause.
4. Players use Rapier's kinematic character controller. Props use dynamic bodies. Colliders come from simplified meshes. Use contact events and scene queries, never distance checks, for gameplay collisions.
5. Seeded randomness only. No `Math.random()` or `Date.now()` in `sim/`.
6. glTF only, optimized with gltf-transform. Clone characters with `SkeletonUtils.clone`. Dispose on unload. Credit asset sources even when CC0.
7. Stay inside the budget preset. Use InstancedMesh or BatchedMesh for repeats. One shadow-casting sun. Warm shaders with `compileAsync` before play. No allocation in update code.
8. Menus and HUD in the DOM, inside safe areas.
9. Audio unlocks on the first gesture and suspends when hidden.
10. Saves are versioned JSON, never raw physics snapshots.
11. No loading screen that blocks play. Show the world first, load the rest behind it. The game must work inside an iframe.
12. Multiplayer is server authoritative. Start with Colyseus 0.18. Never trust client positions.
13. Keep the `window.__game` hooks and tests working after every change. Report what the tests printed, not what should happen.

### Done checklist (run before calling a game done)

1. `npm run build` succeeds; `tsc --noEmit` is clean; `tw lint` reports no stale APIs.
2. `tw check` on the built game: zero console errors, zero failed requests, sane scene summary (player visible, camera not inside geometry).
3. `node --test`: the headless sim gives the same hash twice for the same seed and inputs.
4. Playwright smoke: `__tw.ready` resolves; mode is `play`; holding each move action for 60 ticks moves the player the right way; jump rises and lands; grounded at rest.
5. Frame-rate independence: the same per-tick inputs, driven through the frame loop at simulated 30, 60 and 144 fps, give the same position after the same number of ticks (the final tick count may differ by one because of the accumulator remainder).
6. Replay: the clock frozen before navigation, the same seed and key presses give the same hash on two reloads.
7. Pause: hidden tab and Esc pause the game, stop ticks and suspend audio; resume works.
8. Inputs: keyboard, an injected gamepad and a touch drag all move the player.
9. Budgets: bytes before first interaction at most 5 MB compressed; draw calls and triangles within the preset; `renderer.info.memory` flat after restart.
10. Layouts: plays at 360x640 portrait and 1280x720; pixel ratio capped at 2.
11. Loop: title, play, win or lose, restart, all without a page reload; settings persist across reload.
12. Works inside an iframe with no login and no external requests beyond declared ones.
13. One small canvas screenshot (`tw shot` or `tw sheet`) looks right.
14. Asset credits and licenses listed.
